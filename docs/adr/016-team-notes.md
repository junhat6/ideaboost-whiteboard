# 016: Issue にしない小さな仕事を「チームの付箋」として棚に貼る

2026-11-25。ハッカソンの告知文、会場の電源確認、お礼メールなど、実装ではないチームの仕事を書き留める場所がなかった。Issue にすると、一覧→New→必須項目→Create の手間がかかる。しかも本来 Issue は AI エージェントが作るもので、人が一言だけ書き留める用途には重すぎる。

## 判断

- ボードの左に「チームの付箋」の棚を置き、一言を Enter で貼る。複数行を貼ると 1 行が 1 枚になる（先頭の `-`・`・`・番号は外す）。ボードは文を解析しない。整理や分解は、後から手元の AI に任せる（M1・M2、下記）。
- 保存先は GitHub ではなく、1 つの SQLite Durable Object（`TeamNotesCoordinator`、`/api/team-notes`）にする。GitHub が正本なのは Issue と Project だけで、付箋はそこに書かない。
  - D1 は使わない。理由: 1 つのボードの書き込みを 1 か所で直列化でき、既存の MutationCoordinator（ADR 002）と同じ「明示 queue・requestId 記録・rev 競合」の型をそのまま使えるため。
- 書き込みの規則は Issue の変更と同じにする。
  - 付箋ごとの `rev` で楽観的競合を検出し、古い rev の変更は 409 で止めて現在の付箋を返す。
  - 同じ利用者・同じ requestId の再送は前回の結果を返し、二重に貼らない。本文が違えば 409 で拒否する。
  - DO への転送が失敗したら「結果不明」（503・ambiguous）と返す。画面は自動で再送せず、「最新を取得」で利用者に確かめてもらう。
  - Worker 側の Origin 検査・認証・rate limit を Issue の API と同じ経路で通す。利用者 ID は検証済みのものだけを使い、要求ヘッダーの値は信じない。
- 上限: 本文 200 文字、1 回に 20 枚、表示中 300 枚。剥がした付箋は直近 50 枚だけ残し、元に戻せるようにする。
- 確定・済み・剥がすは人だけが行う。全画面（`f`）では棚を隠し、ボードだけを見せる。`T` で一言入力へ移る（入力中・ダイアログ・全画面では反応しない）。
- 静的プレビュー（`scripts/preview.mjs`）だけが `sample: true` の見本を返し、画面は「サンプル表示です。付箋は保存されません。」と明示して保存しない。本番の Worker は見本を返さない。

### 機能フラグ（2026-11-25 追記、#8 M0）

- Worker の変数 `TEAM_NOTES_ENABLED` が `"true"` のときだけ `/api/team-notes` を開く。未設定・それ以外は、認証・Origin 検査の後、問い合わせ文字列の検査より前に `404 not_found` を返し、DO へ転送しない。本番の `wrangler.jsonc` は `"false"`。理由: develop は release ループで毎時本番へ出るため、ログイン必須化（#10）前に匿名で書ける付箋を出さない。
- 画面は `/api/team-notes` の GET 結果で有効かを知る。棚は HTML で `hidden` のまま始め、200 なら出し、404 なら出さずに定期取得もしない。board API に flag を載せる案は採らなかった。理由: GitHub 境界（`server/github.mjs`）と board の DO 読み取りに付箋の都合を持ち込まずに済み、無効時は Worker の 404 だけで画面も API も同じ根拠で閉じるため。代わりに有効時は最初の GET が返るまで棚が出ず、1 回だけボード幅が変わる。
- 棚が現れるとボードの幅が変わり描き直されるため、進行中の native drag があれば dragend/drop まで棚の表示を後へ回す（ドラッグ中のカードを DOM から外さない）。
- 無効時の確認の GET は、public-temporary でも共有の public-read の rate limit を使わない（DO も GitHub も呼ばずに 404 で終わるため）。有効時は従来どおり rate limit を通す。
- POST に JSON でない応答（前段の 502/524 の HTML など）が返ったら、DO で反映済みかもしれないので結果不明として扱い、自動で再送しない（`api-adapter.js` と同じ）。
- ローカルで有効にするときは `.dev.vars` に `TEAM_NOTES_ENABLED=true` を書く（git に入らない）。本番で有効にするのは #10 の後に人が決める。
- 実際の AI クライアントで試すための dev 環境（別 Worker・付箋有効・GitHub へ書かない）は [ADR 017](017-dev-environment.md)。

### 本番で有効にする（2026-11-25 追記、オーナー方針）

- 本番の `TEAM_NOTES_ENABLED` を `"true"` にした。理由: オーナー方針「機能フラグで閉じたまま本番に置かない」。ログイン必須化（#10）は Cloudflare の Zero Trust の有効化で止まっており（権限）、それを待つと棚がいつまでも出ない。
- public-temporary の間、付箋は**匿名で書ける**（作者は `public-anonymous`）。これは実 Issue の匿名編集と同じ承認の内側にある: 秘密の path・固定 host・Origin 検査・共有の rate limit を同じ経路で通る。付箋は GitHub に書かず、DO の中だけに残る。AI の op（直し案・添付・提案）は `/mcp` だけが付けられ、`/mcp` は public-temporary では常に 404 なので、匿名の間に AI を名乗る書き込みは入らない。
- rate limit の key を付箋だけ分けた（`public-notes-read` / `public-notes-write`）。棚は 30 秒ごとに読み直すので、ボードと同じ `public-read` を使うと、数人が棚を開いているだけでボードの読み取りが 429 になるため。上限は同じ 30 回 / 60 秒（場所ごとの近似）。
- 戻し方: `TEAM_NOTES_ENABLED` を `"false"` にして昇格すると、棚と API は 404 に戻る。DO の付箋は消えない。
- 採らなかった案: ログイン必須化まで待つ（方針に反する）、付箋だけ読み取り専用で出す（貼れない棚は使い道が無い）。

### M1: AI の直し案・添付・提案付箋（2026-11-25 追記、#8）

手元の AI（M2 でリモート MCP から）が付箋に「付ける」ものを 3 種類にし、採否は人が決める。

- **データ形**（`worker/team-notes.ts`）
  - 直し案（赤ペン）: 付箋の `suggestions[]` に `{ id: "s_…", before, after, by, at }`。`before` は案を出した時点の本文。
  - 添付: 付箋の `attachments[]` に `{ id: "a_…", kind: "text" | "url", value, label?, state: "pending" | "kept", by, at }`。人が「残す」と `kept` になる。
  - 提案付箋: `proposal: true` の付箋を、通常の一覧（`meta.ids`）とは別の `meta.proposals` に置く。人が採用すると `proposal` を外して通常の一覧の先頭へ移し、rev を上げる。GET は `{ notes, proposals }` を返す。
  - 直し案や添付を付けても、付箋の本文・状態・rev は変えない。AI の書き込みのせいで人の編集が競合にならないようにするため。rev が上がるのは、本文が変わる直し案の採用だけ。
- **権限**（サーバーで強制）
  - 書き手の種別 `actor` は、DO への内部ヘッダー `x-team-notes-actor: ai` だけで決まる。これを付けられるのは Worker の内部の入口（M2 の MCP）だけ。Worker はブラウザから届いた同名ヘッダーをすべての要求で消すので、ブラウザから AI を名乗っても人として扱われる。値の比較は完全一致（`AI` などは人）。
  - AI 専用の op は `suggest` / `attach` / `propose`。それ以外（`create` / `edit` / `done` / `remove` / `restore` / `accept` / `reject`）は人だけ。種別と op が合わなければ、AI には 403 `human_only`、人には 403 `ai_only` を返し、何も記録しない。人が AI の op を偽装して直し案を付け、自分で採用する、という経路は作らない。
  - 利用者 ID は検証済みの `x-verified-user-id` だけを使う。requestId の記録は、AI のものを `ai:` 付きの別の鍵に分ける。
  - 採否は `accept` / `reject` で行う。`item` が無ければ提案付箋そのもの、`s_` は直し案、`a_` は採用待ちの添付が対象。
- **競合**: 直し案は、付けるときも採用するときも `before` と現在の本文の一致を確かめる。違えば 409 `note_conflict` を返し、現在の付箋を返す。画面は最新を取り直し、採用ボタンを無効にして「本文が変わったため採用できません」と文字で示す。却下は本文を変えないので、競合を確かめない。
- **上限**（サーバーで検証）: 直し案の本文 200 文字（付箋と同じ）。保留中の直し案は付箋 1 枚に 5 件。添付は文 2000 文字か URL 1 本（2000 文字、表示名 100 文字）で、採用待ちは 1 枚に 5 件、残せるのは 10 件。採用待ちの提案付箋は 20 件。超えたら 409（`suggestions_full` / `attachments_full` / `proposals_full`）。
- **URL**: http/https だけを受け付ける。利用者名やパスワードを含むもの、空白や制御文字を含むもの、`//` で始まるものは拒否する。画面も同じ判定をもう一度行い、通ったものだけを `<a target="_blank" rel="noopener noreferrer" referrerpolicy="no-referrer">` にする。それ以外と文の添付は textContent で見せる。
- **済みの付箋**: 済みにする前に付いた直し案は消さずに残し、画面には出さない（済みを外すと出る。`notes_list` は `done: true` とともに返す、ADR 018）。新しい直し案は 409 `note_done` で受け付けない（画面は済みの付箋に直し案を出さず、人が採否できないため）。添付は済みの付箋にも付けられ、画面も済みの付箋の添付を見せて採否できる（終えた仕事の成果物を後から付けるため）。
- **却下の扱い**: 却下した直し案・添付・提案付箋は消し、履歴に残さない。理由: v1 では AI の案を後から見返す使い道がまだ無く、残すと保存量と画面の項目が増えるため。同じ要求の再送は requestId の記録が前回の結果を返すので、消しても二重適用は起きない。必要になったら、剥がした付箋と同じく直近 N 件の履歴として足す。
- **書き込みの規則**は M0 と同じ（明示 queue、requestId の二重適用防止と再利用拒否、転送失敗は結果不明で自動再送しない）。機能フラグが無効なら、新しい op も Worker で 404 になり、DO へ届かない。
- **画面**: 直し案は「直し案」の文字、取り消し線の元の文、案の文を並べ、「採用」「却下」を置く。添付は付箋の下の折りたたみ（開閉は描き直しをまたいで保つ）で、採用待ちには「残す」「却下」を置く。提案付箋は「AI の提案（採用待ち）」の欄に、破線の枠と「提案」の文字で通常の付箋と分けて出す。ボタンはすべて Tab で届き、Enter で押せる。ボタンの上ではボードの 1 文字ショートカットを発火させない。

## 採用しなかった案

- 付箋を GitHub の Issue や Discussion に保存する: Issue を作る手間を減らすという目的に反する。また、実 Issue をテスト目的で変更しない規約とも衝突する。
- ブラウザーの localStorage だけに保存する: チームで共有できない。
- 貼った時点で AI が文を解析・分類する: 人の一言と AI の解釈のずれが見えないまま確定してしまう。v1 では生のまま保存する。解釈は赤ペン（直し案）として見える形で返す（M1）。

## 今後（この ADR の範囲外）

- M2: リモート MCP（`notes_list` / `note_suggest` / `note_attach` / `note_propose`）は [ADR 018](018-remote-mcp.md) で実装した（本番では無効、dev で有効）。M1 の `suggest` / `attach` / `propose` を AI の種別で呼ぶ内部の入口で、人が採否を決める。本番で有効にするのは、ログイン必須化と managed OAuth の実機確認の後。
- アプリ全体のログイン必須化（Cloudflare Access）。利用者の承認は済んでいるが、手順書を確認してから切り替える。
- 付箋を Issue にする操作は v1 では入れない。

## 検証

- M1: `tests/team-notes.test.ts` で、直し案の採用・競合・却下、AI と人の権限の偽装の拒否、Worker が種別ヘッダーを消すこと、URL の拒否と上限、提案付箋の採否、AI の requestId 再送、保存失敗時の結果不明を確かめる。`tests/browser/team-notes.spec.ts`（1920×1080・2560×1440）で、本物の TeamNotesStore をメモリ上で動かし、キーボードだけでの採否、崩れないこと、採用できない直し案の表示、結果不明時に再送しないこと、危険な URL や HTML を文字としてだけ見せることを確かめる。

- `tests/team-notes.test.ts`: requestId の二重適用防止と再利用拒否、rev 競合、剥がす・戻す、本文と件数の検証、Worker の Origin 検査と検証済み利用者、転送失敗時の結果不明。
- 無効時: `tests/team-notes.test.ts` で未設定・`"false"` などの GET/POST が 404 で DO へ転送しないこと、チームモードでは認証が先に走ること。`tests/browser/team-notes.spec.ts` で 404 なら棚が出ず、ボードが棚の導入前と同じ全幅（main の padding 8px の内側）であること、ドラッグ中に棚が現れてもカードが DOM から外れずに落とせること、JSON でない 502 を結果不明として扱い再送しないこと。
- `tests/browser/team-notes.spec.ts`（1920×1080・2560×1440）: Enter と複数行での貼り付け、キーボードだけでの済み・剥がす・元に戻す、その場での編集と Escape、競合時の最新表示、結果不明時に再送しないこと、サンプル表示、棚の折りたたみ、全画面で隠れること、ボードが残りの幅に収まること。
