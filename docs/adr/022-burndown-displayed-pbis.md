# 022: バーンダウンをボードで表示中のPBIに合わせ、Close済みPBIを記録に残す

2026-11-27。スプリントレビューで、ボード（Close済みPBIを含む15 PBI）とバーンダウンの数字が合わず、何を計算しているのか分からなかった。

## 原因

- 毎日の記録は view 16（`is:open`）のPBIだけを読んでいた。PBIをCloseすると、その日に配下の完了作業ごとスプリントから消え、全体見積も減る。Sprint 12ではClose済み11 PBI（41件・82h、すべて完了）が1件も入っていなかった。
- 逆に、ボードに出していないOpenなPBI 16件はスプリント全体として入っていた。

## 判断

- 記録時（`GET /api/burndown` の内部観測）は、進行中スプリント（正式な割当期間が現在を含む）のうち最も早い開始日以降にCloseしたPBIも追加で読む。条件はview条件の`is:open`を`is:closed closed:>=<開始日のUTC日付>`に置き換えたもの。開始はJST 00:00なのでUTC日付は前日になり、開始日のJST 1日分を確実に含む。前スプリント中のCloseが少し混ざっても、そのタスクのmilestoneで振り分けるので集計は変わらない。
- 記録のscope文字列はview条件のままにし、既存の履歴と連続させる。
- 応答にPBI別の集計（`pbis`）と、日ごとの再計算のPBI別内訳（`rebase.observations[].byPbi`）を足す。チャートはボードで表示中のPBIだけを合計して描く。表示中でもそのスプリントの作業がないPBIは0として扱い、件数を注記する。
- PBIを持たない古い記録の日は、PBI別に分けられないため空白にする。全体値を流用・按分しない。
- 保存する記録はスプリント全体のまま。表示の絞り込みは利用者ごと（ブラウザーごと）のPBI選択に従うため、開く人によって数字が変わる。チャートには「ボードで表示中のPBI n件のうち…」と注記する。

## 採用しなかった案

- スプリント全体（Close済みを含む）を集計する: 誰が開いても同じ数字になるが、レビューで見せるボードと一致しない。利用者がボードとの一致を選んだ。
- 記録自体を表示中のPBIで保存する: ブラウザーごとの選択で共有の記録が変わってしまう。
- Close済みPBIの読み込みを「過去10日」（ボードのopt-in）に合わせる: スプリントが10日を超えると、途中でCloseしたPBIが記録から外れて全体見積が減る。

## 限界

- 過去の記録に存在しない作業は、従来どおり「当時は未完了」として再計算する。Sprint 12では作業の大半が11/26に作成・Closeされたため、赤線は11/26まで横ばいで、その後に落ちる。これはGitHub上の記録どおりで、実際の作業日は推測しない。

## 検証

`server/recent-closed.test.mjs`（進行中スプリントの開始日でCloseの範囲を決める）、`tests/burndown.test.ts`（PBI別の再計算・PBIなしの記録はnull）、`tests/burndown-axis.test.ts`（表示中PBIだけの合計、内訳なしの日は空白、旧APIは全体のまま）。
