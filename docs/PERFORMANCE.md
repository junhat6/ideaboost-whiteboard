# 初期表示とIssue表示の改善 — 2026-10-26

## 原因と変更

本番の初期表示はGitHub Projectの取得待ちが支配していた。改善前の段階別実測は公開確認796ms、metadata393ms、Project3ページ2,359/2,107/1,167ms、view行522ms、担当者351ms、終了時公開確認415ms。初期healthもboardの前に実行されるが約38–52msで主因ではなかった。

- 全Projectの本文・担当者・Statusを読む代わりに、正式な親子関係・Project順・マイルストーンを軽い索引としてページング。view 16はPBI選択にのみ適用し、子・孫タスクは索引から展開する。
- 完全な本文・担当者・revisionとStatusは、表示対象Issue/Project itemだけを最大50件単位でまとめて取得する。対象外の親は重複を除いて必要情報を取得する。取得できないIssue/Statusは欠けた編集カードとして返さずエラーにする。
- metadata→view行、Project索引、担当者一覧を独立した枝として並列化。初回installation token生成はsingle-flightにし、並列枝が重複発行しない。既存tokenの期限付きメモリー再利用を維持。
- 固定repository照合はサーバーで各項目に行う。Project索引にviewのPBIフィルターをかけない。公開確認は開始・終了で毎回行う。
- ボードのキャッシュやlocalStorageスナップショットは導入していない。初回・再訪ともGitHubを読み、秘密やボードを新しい永続ストレージへ保存しない。mutationは引き続き全write scopeを取得し、DOと独立した最終preflight/readbackを使う。
- `Server-Timing`に段階名と時間だけを付ける。Issue本文・利用者情報・秘密は含まない。

付箋クリックはネットワーク要求を発行していなかったが、背景更新中の共通`pending`判定でクリック自体を捨てていた。読み取り中も取得済みIssueの開閉を許可し、最新確認中と明示する。確認完了まで編集を無効化し、書き込み中のロックは維持する。失敗時は前回取得内容と表示し、再取得できる。更新終了時の重複全描画も除いた。

ユーザー指定に従い詳細画面は左80vw。編集・保存と更新状態は本文より上に配置した。Escape/背景クリックは未保存内容の破棄確認を共用する。
