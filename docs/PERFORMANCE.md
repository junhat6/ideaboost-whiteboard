# 初期表示とIssue表示の改善 — 2026-10-26

## 原因と変更

本番の初期表示はGitHub Projectの取得待ちが支配していた。改善前の段階別実測は公開確認796ms、metadata393ms、Project3ページ2,359/2,107/1,167ms、view行522ms、担当者351ms、終了時公開確認415ms。初期healthもboardの前に実行されるが約38–52msで主因ではなかった。

- 全Projectの本文・担当者・Statusを読む代わりに、正式な親子関係・Project順・マイルストーンを軽い索引としてページング。view 16はPBI選択にのみ適用し、子・孫タスクは索引から展開する。
- 完全な本文・担当者・revisionとStatusは、表示対象Issue/Project itemだけを最大50件単位でまとめて取得する。対象外の親は重複を除いて必要情報を取得する。取得できないIssue/Statusは欠けた編集カードとして返さずエラーにする。
- metadata→view行、Project索引、担当者一覧を独立した枝として並列化。初回installation token生成はsingle-flightにし、並列枝が重複発行しない。既存tokenの期限付きメモリー再利用を維持。
- 固定repository照合はサーバーで各項目に行う。Project索引にviewのPBIフィルターをかけない。公開確認は開始・終了で毎回行う。
- ボードのキャッシュやlocalStorageスナップショットは導入していない。初回・再訪ともGitHubを読み、秘密やボードを新しい永続ストレージへ保存しない。mutationは引き続き全write scopeを取得し、DOと独立した最終preflight/readbackを使う。
- `Server-Timing`に段階名と時間だけを付ける。Issue本文・利用者情報・秘密は含まない。

付箋クリックはネットワーク要求を発行していなかったが、背景更新中の共通`pending`判定でクリック自体を捨てていた。読み取り中も取得済みIssueの開閉を許可し、最新確認中と明示する。当時は確認完了まで編集を無効化した。現在はADR005で入力を即時許可し、保存時にfresh照合する。書き込み中のロックは維持する。失敗時は前回取得内容と表示し、再取得できる。更新終了時の重複全描画も除いた。

ユーザー指定に従い詳細画面は左80vw。編集・保存と更新状態は本文より上に配置した。Escape/背景クリックは未保存内容の破棄確認を共用する。

新規client＋共有結果ありでは3回とも3.5秒以内、fresh pathは中央値で未達。最初の5.179秒は新しいread DOへの配信後最初の要求で結果がなかった。他2回はclient初回だがserver/tokenはwarmで、初期snapshot要求ヘッダーを外して共有結果を使わない経路を測った。3回すべてを物理的なcold isolateとは呼ばない。

共有結果の年齢は新規clientで1.751–2.340秒、再訪で1.250–1.433秒。上限60秒の古い表示を測った結果ではない。画面に元の取得時刻・経過秒数・最新確認中を出し、直後にfresh取得する。fresh完了までは閲覧のみ。共有結果が60秒を超えた場合・memory eviction・翌朝・誰も利用していない後の最初のアクセスは4–6秒程度のfresh pathへ戻り得る。

残るfreshの主因はbootstrap、その後のindexページとPBI→子Issue問い合わせ、終了時の公開確認。測定例はbootstrap699ms、並列のindex874+551msとPBI523+子879ms、最終公開確認365ms。snapshotはこの往復を前回の完全な結果で先行表示する方式で、GitHubの新規応答そのものを2秒に短縮したわけではない。

**次の判断**: 誰も開いていなかった後も3.5秒を目指すには、閲覧要求から独立した最新projectionの維持が必要。GitHub App Webhook設定＋新しい検証secret＋bounded persistent projection/更新処理の設計・承認が候補になる（公開状態の毎回確認は継続）。この設定は今回実施していない。Webhooksでも外部イベント遅延や欠落時のreconciliationが必要で、常時最新や3.5秒のSLAを無条件に保証しない。

最終実画面では1920でcold fallback、続く2560で共有hitを確認。2560は「直近の取得結果・最新確認中・最終取得時刻（2秒前）」を表示し、右80%詳細の編集はfresh完了後に解除された。両画面の完全本文、編集キャンセル2回、6PBI/14cards、全画面、POST0、JavaScriptエラー0を確認。53 backend / 68 browserのCIも成功。
